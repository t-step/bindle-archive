# release-please-sync — design

**Status:** Spec, v1 · **Issue:** [thomas-estep/bindle#137](https://github.com/thomas-estep/bindle/issues/137)

## Problem

The v0.5.0 release (the first cut through the local Release Please strategy,
`bin/release-strategies/local-release-please.sh`) left two artifacts stale:

1. **`VERSION`** — `release-please-config.json` lists it under `extra-files`,
   but Release Please's generic file updater only rewrites lines carrying an
   `x-release-please-version` annotation comment. Bindle's `VERSION` is a bare
   `MAJOR.MINOR.PATCH` with no such annotation (adding one would break every
   reader that expects a pure semver string), so the entry is a silent no-op.
   The v0.5.0 release PR left `VERSION` at `0.4.0`; a human had to notice and
   hand-fix it (`fix: sync VERSION to 0.5.0`).
2. **`RELEASE-MANIFEST.json`** — a provenance snapshot (capability inventory,
   installed surfaces, tool versions, changelog range) generated by
   `bin/release-manifest.py`, previously only ever called from `bin/release.sh`.
   Release Please doesn't know this file exists, so it now lags at `0.4.0`
   while the actual release is `0.5.0`.

`docs/workflows/release-captain.md` already commits to the target
architecture — Release Please owns `VERSION`/`CHANGELOG.md`; `bin/release.sh`
is legacy/fallback publication tooling only — but nothing currently keeps
`VERSION` and `RELEASE-MANIFEST.json` in sync with what Release Please
actually proposes.

## Constraint that shapes this design

GitHub Actions is currently billing-blocked on this repo (pushing a `v*` tag
fires `release.yml` but the job never starts). Release Please is already
invoked **locally** here (`local-release-please.sh`, driven by a human or the
`release-captain` skill) — not via a GitHub App or Actions workflow. Any fix
that depends on a *new* Actions trigger would be silently inert today,
reproducing the exact "looks handled, isn't" failure this issue is about. The
fix must run locally, as an explicit next step in the existing apply flow.

## Approach

A new script, `bin/release-please-sync.sh`, runs as the step immediately
after `bin/release-strategy.sh apply` in the release-captain flow. It updates
the *already-open* Release Please PR branch in place — it never creates a new
PR, never touches `main`, never tags, merges, or publishes.

### Why sync onto the PR branch, not after merge

Syncing before merge means the human reviewing the release PR sees the final,
consistent `VERSION` + `RELEASE-MANIFEST.json` state as part of the same
review — not a surprise follow-up commit to `main` after the fact, which
would also require punching a hole in the `no-commit-to-branch` protection
`main` currently has. It also means `RELEASE-MANIFEST.json`'s `changelog`
field can read the version's `## [x.y.z]` CHANGELOG section directly, because
Release Please has already written it on that branch.

### `bin/release-please-sync.sh` — behavior

Verbs mirror `local-release-please.sh` (`dry-run` / `apply --approval-token
<ephemeral>`), for the same reason: this script performs its own `git push`
(an external mutation per `docs/workflows/release-captain.md` §2) and should
carry its own explicit grant rather than ride in silently on the strategy's
approval.

1. **Find the release PR.** `gh pr list --state open --label "autorelease:
   pending"` — Release Please's own convention for tagging its release PR.
   Zero or more-than-one matches is a hard stop (fail closed; never guess
   which PR).
2. **Read versions.** New version from `origin/<head-branch>`'s
   `.release-please-manifest.json` (the "." key); previous version from
   `origin/<base-branch>`'s (i.e. `main`'s current value — matches what's
   already released).
3. **Idempotency check.** If `origin/<head-branch>`'s `VERSION` already equals
   the new version, report "already in sync" and exit 0 — safe to re-run,
   safe if `apply` is invoked more than once for the same PR.
4. **dry-run** stops here and reports what *would* change (PR number, branch,
   old/new version) — zero mutation.
5. **apply**, in an isolated `git worktree` tracking the head branch:
   - write `VERSION` with the new version;
   - run `bin/check.sh` and `bin/test-install.sh` — the same invariant
     `bin/release.sh` upholds before trusting its own manifest; abort (no
     commit, no push) on failure;
   - run `python3 bin/release-manifest.py --version <new> --previous <old>
     --verify-determinism` then `--emit`;
   - `git add VERSION RELEASE-MANIFEST.json`, commit
     `"chore: sync VERSION + RELEASE-MANIFEST.json to vX.Y.Z"`;
   - push to `origin HEAD:<head-branch>` — updates the existing open PR;
   - remove the worktree.

### `release-please-config.json`

Drop the dead `"extra-files": ["VERSION"]` entry (it never worked) and leave
a one-line comment-equivalent note in `docs/workflows/release-captain.md`
pointing at the new script, so a future reader doesn't reintroduce the
no-op entry expecting it to do something.

### `RELEASE-MANIFEST.json`'s fate (issue's decision point 2)

**Kept, and now regenerated automatically** rather than retired. It carries
real content Release Please's own output doesn't (capability/installed-
surface snapshot, tool versions, a tamper-evident checksum) and the
release-captain contract's Step 1 explicitly cross-checks against it. Given
regeneration is now a cheap, automatic side effect of the same sync step that
fixes `VERSION`, there's no reason to give up that provenance value.

### Docs / contract updates (issue's decision point 3)

- `docs/workflows/release-captain.md` — Step 6 gains the sync step; Section 5
  notes `RELEASE-MANIFEST.json` is now auto-regenerated under the Release
  Please flow, not just a `bin/release.sh` artifact.
- `skills/release-captain/SKILL.md` — "Apply" section runs
  `bin/release-please-sync.sh dry-run` / `apply --approval-token` as the next
  command after the strategy's own apply, under the same second approval
  gate (still repository-mutation-only; no new authority class).
- `docs/release-manifest.md` — documents the new automatic generation path
  alongside the existing `bin/release.sh` path.

## Out of scope

- `bin/release.sh`'s legacy path currently hard-fails immediately (it greps
  for a `## [Unreleased]` CHANGELOG section that no longer exists post-RP
  migration). Real bug, unrelated to this issue's acceptance criteria — flag
  as a follow-up issue, don't fix here.
- No asset publication, draft-release orchestration, or tag/GitHub-Release
  automation. Those are publication-authority actions this issue doesn't ask
  for.
- No rename of `VERSION` → `version.txt`. Renaming would ripple through 9+
  existing readers (`check.sh`, `check-inventory.py`, `doctor.sh`,
  `install.sh`, `new.sh`, `release-evidence.py`, `local-release-please.sh`,
  etc.) for no behavioral gain over syncing the existing file in place.

## Testing

`bin/test-release-please-sync.sh`, following the repo's `bin/test-*.sh`
fixture convention (see `bin/test-release-strategy.sh` for the pattern of
stubbing external commands via env-var override, e.g. a fake `gh`/`git`
resolvable via `PATH` injection). Cases:

- zero matching PRs → hard stop, no mutation;
- two matching PRs → hard stop, no mutation;
- already-in-sync → no-op, exit 0, no commit;
- dry-run → reports the diff, zero mutation (verify via git ref unchanged);
- apply with a failing `bin/check.sh` → aborts, no commit, no push;
- apply, clean → `VERSION` and `RELEASE-MANIFEST.json` land on the head
  branch in one commit, pushed, worktree removed;
- apply without `--approval-token` → refused, matching
  `local-release-please.sh`'s existing refusal shape.

## Repo housekeeping

Per this repo's capability-inventory convention (`bin/check-inventory.py`),
the new `bin/release-please-sync.sh` needs a `script`-type row in
`capabilities.json`; this spec doc and its companion plan doc each need a
`not_a_capability` ledger entry (or the design-doc / plan-doc pattern already
used by `docs/design/2026-07-12-release-manifest.md` and
`docs/plans/2026-07-12-release-manifest.md`). `make check` fails the build
until these are classified — the implementation plan must include this step.

## Non-goals

Same non-goals as `docs/release-manifest.md`'s existing list (no signing, no
automatic GitHub Release publication, no capability-level diff between
releases) — this design doesn't change that contract, only how the manifest
gets triggered.
